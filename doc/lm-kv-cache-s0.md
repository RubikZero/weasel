## 0. 一句话结论

**不用重训、也不用改对齐方式**：把"远端前缀"的 K/V 冻结，只把**最后 K 个 token + `[MASK] [SEP]`**
放在一个**双向**的小块里重算，就能复现今天的排序——
K=32 时 top1/MRR **与基线完全相同**（逐例 top1 一致率 99.84%），K=16 时 99.63%（Δtop1 −0.08pt）。
单步耗时从 O(ctx) 降到 O(K)：ctx=64 时 2.3×（K=32）～4.5×（K=8），ctx=256 时 6.4×～13.3×。

真正**行不通**的是另外两种掩码：全因果（C）在现权重下掉 2.4pt，prefix-LM + 因果块掉 1.4pt。

（即部署的那个 best checkpoint）完全一致 → 评测口径可信。

要点：
1. **尾块必须双向**。"块内因果"（`frozen_tail*`）比"整块冻结"还差，说明真正重要的是
   `[MASK]` 附近的 token 仍能与 `[MASK]` 互相看见；而远端前缀冻结几乎无损。
2. **K 是唯一的旋钮**：K=8 已经 99.40%，K=16 → 99.63%，K=32 → 聚合指标与基线完全相同。
3. **对齐/位置可以不动**：所有 `frozen_bi*` 都使用今天的右对齐布局与完全相同的 position。
   另外单独量了"位置整体 +1"的影响：−0.24pt / 97.8% 一致率 → 窗口滑动造成的错位不致命，
   但**没有必要**为此改对齐（本轮方案本来就不移动位置）。
4. **不需要重训**：这三点合起来意味着 A/C 方案里"必须微调"的前提不成立——
   用今天的权重就能拿到 99.6%+ 的一致性。

## 2. 延迟（ONNX Runtime CPU，intra_op=4，15 次取中位数）

`full` = 今天一次调用的成本（`ctx+3` 个 token）；`prefix` = 一次性编码远端前缀；
`step` = 冻结前缀 + K+2 个 token 的块（含 8 个缓存张量的输入/输出拷贝）；
`speedup` = full / step。rows = 批内行数（重排菜单/beam 宽度）。

**K=16**（推荐）：

| ctx_len | rows | full ms | prefix ms | step ms | cache MB | speedup |
|---|---|---|---|---|---|---|
| 32 | 16 | 17.11 | 7.21 | 10.72 | 2.0 | 1.60× |
| 64 | 16 | 29.78 | 13.00 | 9.50 | 6.0 | 3.14× |
| 96 | 16 | 43.07 | 23.25 | 10.14 | 10.0 | 4.25× |
| 128 | 16 | 51.44 | 31.33 | 9.07 | 14.0 | 5.67× |
| 200 | 16 | 97.74 | 60.17 | 11.95 | 23.0 | 8.18× |
| 256 | 16 | 115.63 | 76.18 | 11.56 | 30.0 | **10.01×** |
| 256 | 1 | 9.23 | 6.18 | 1.63 | 1.9 | 5.66× |

**K=8**：step 6.5–8.8 ms（rows=16）→ ctx=64 时 4.54×、ctx=256 时 **13.30×**；一致性 99.40%。
**K=32**：step 14.0–18.3 ms → ctx=64 时 2.28×、ctx=256 时 6.44×；一致性 99.84%。

三个可直接用于决策的观察：
1. **step 基本与 ctx 无关**（K=16：9.1–12.0 ms，只随前缀变长略有增长，主要来自缓存拷贝：
   ctx=256 时缓存 30 MB），而 `full` 随 ctx 线性增长 → 增益随上下文变长而放大。
2. **短上下文几乎没有收益**：ctx=32、K=16 只有 1.60×，因为尾块本身就占了窗口的一半。
   这正是你们现在自适应窗口（32–48）下的常见情形 → **字词重排的短上下文收益有限**。
3. **prefix 编码是一次性成本，约等于一次 `full`**。所以缓存只有被**重复使用**才划算：
   - 单次请求内（beam 每步 / 重排的多个候选长度）：省下每步的 O(ctx)；
   - 跨请求（同一 ctx 多次打分，例如用户继续敲拼音时 ctx 不变）：连 prefix 编码也省掉，
     这才是收益最大的一档，也正是需要"退格/光标/失效"逻辑的地方（见第 4 节）。

## 3. 导出侧结论（S1 的准备工作，本轮已全部验证）

导出两张图并逐项校验（脚本自带）：

| 图 | 输入 | 输出 | 校验结果 |
|---|---|---|---|
| `encode_kv.onnx` | `input_ids`, `attention_mask`, `position_ids` | 每层 K/V（后缀 `total_seq` 动态） | 对 torch 最大差 **6e-06**，前缀长度 64 与 9 都通过 |
| `step_kv.onnx` | `input_ids`, `past_attention_mask`, `position_ids`, 每层 past K/V | `logits`(B,2,V)、每层 present K/V | 对 torch 最大差 **1.1e-05**，块长 34/18/10/12 都通过 |

踩到并修掉的坑（都会直接影响 S1，值得先记下来）：
1. **`torch.onnx.export` 会把模块留在 train 模式** → 校验时若不再 `.eval()`，比较的是
   "dropout 开" vs "dropout 关"，会得到 1.7~2.5 的假差异（我因此白追了三轮）。
2. **Python 整数形状会被烧进图里**：`b, n = ids.shape` 之后用 `view(b, n, ...)` 或
   `expand(b, heads, n, ...)` 都会固定成导出时的长度 → 必须写成
   `x.view(x.size(0), x.size(1), ...)`、`expand(-1, heads, -1, -1)`、`flatten(2)`。
3. **位置必须作为显式输入**：从 `past_key_values` 长度推位置会被烧成常量，
   导致图只在导出时的前缀长度下正确。
4. **不要用动态下标读 `[MASK]`**：改为输出最后两个位置 `(B, 2, V)`，由调用方取第 0 行
   （`narrow(1, size(1)-2, 2)`），这样下标不依赖运行期长度。
5. **`past_attention_mask` 必须作为输入**：缓存里的 PAD 位置要按前缀自己的 mask 屏蔽，
   否则已经失效的 PAD key 会被 `[MASK]` 看见（不一致，实测会让一致性再掉一点）。
6. 必须走 `dynamo=False`（legacy TorchScript 导出）：本图有 10 个动态张量，
   dynamo 导出器无法把 `dynamic_axes` 转成 `dynamic_shapes`，直接报错。

## 4. 对方案选择的影响

| 方案 | S0 结论 |
|---|---|
| **A（prefix-LM 掩码）** | 收益可以直接拿，但**掩码不该是 prefix-LM 的因果版**：正确的是"冻结前缀 + 块内双向"。用现权重即可，**S3 微调从关键路径上移除**（除非想把 K 压到 4 以下）。跨请求复用所需的失效逻辑与 C 相同。 |
| **B（encoder–decoder）** | 仍是"整句质量"路线的选项，但对**缓存收益不再是必需**：A 已经拿到同样的每步 O(K)。若做 B，本轮的 `encode_kv.onnx` 就是它的 encoder 侧起点。 |
| **C（全因果）** | 现权重下 −2.42pt，**必须先微调**才有资格进入比较；且没有额外收益（A 已能跨按键复用，见下）。建议暂缓。 |

**跨请求复用（真正的大头）需要处理的事件**（与上一轮讨论一致，量级终于有数了）：
- 继续敲拼音：ctx 不变（`GetContext()` 只取 `surrounding_text`/`commit_history`）→ 缓存可直接复用；
- 退格删拼音：不影响 token 序列，只需把解码状态截到新的音节数；
- 改选候选 / 上屏 / 退格已上屏文字 / 光标移动 / 切窗口：token 序列变化 → 从最长公共前缀处截断或重置。
  位置漂移的代价已量：整体 +1 位移 → −0.24pt、97.8% 一致（可容忍，但"能证明是延伸才复用"仍是安全默认）。

## 5. 建议的下一步（S1）

1. **按 K=16 实现**（精度 −0.08pt、一致性 99.63%、ctx=64 时 3.1×、ctx=256 时 10×）；
   若要求聚合指标完全不变，用 K=32（2.3×–6.4×）。
2. 插件侧要动的是：缓存张量生命周期、beam 剪枝时的行重排、与 `ScoreCandidatesCancellable`
   的分块取消共存、以及"ctx 快照"作为缓存键 + 失效策略。
3. 先接**请求内**缓存（无失效逻辑）并跑 `ipc_latency_test.ps1` 验证端到端；
   再接**跨请求**复用并补退格/光标/切窗口用例。
4. 需要保留的既有验收线：`testset_eval` 的重排指标（本轮的 `base_right` 0.8985 即基线）。
